# Архитектура маркетплейса

Спроектирован маркетплейс с персональной лентой, каталогом, пользователями, заказами, платежами и уведомлениями. В коде реализован только каркас сервиса каталога с `/health`. Бизнес-логики нет.

## C4 Container

![Архитектура маркетплейса](docs/c4-container.png)

На диаграмме показана проектируемая система. Web — веб-приложение для покупателей и продавцов; остальные приложения выполняют отдельные задачи. Реально запускается только каркас Catalog.

## Домены, сервисы и данные

| Домен | Сервис | Ответственность | Собственные данные |
|---|---|---|---|
| Пользователи | Users | Вход, профили, роли покупателей и продавцов | Учётные записи, роли, email |
| Каталог | Catalog | Управление товарами, ценами и наличием | Карточки, категории, цены, остатки, резервы |
| Персональная лента | Feed | Подбор и сортировка товаров | Выбранные пользователем категории |
| Заказы | Orders | Создание заказа, расчёт стоимости товаров, изменение статуса | Состав, количество, цены на момент покупки, сумма, статус |
| Платежи | Payments | Расчёт суммы к оплате, работа с платёжным провайдером и учёт результата | Сумма, валюта, идентификаторы и статусы платежей |
| Уведомления | Notifications | Отправка писем о статусах заказов | Задания отправки и их результаты |

У каждого сервиса своя PostgreSQL. Общей БД нет; доступ к чужим данным выполняется через API или сообщения. Web не владеет предметными данными. RabbitMQ хранит сообщения для доставки получателям.

Персонализация простая: товары выбранных категорий показываются первыми, внутри группы — сначала новые. Без выбранных категорий отображается общий список.

Допущения: один заказ содержит товары одного продавца; суммы хранятся в копейках, валюта — RUB; скидки и доставка не учитываются. Сумма платежа равна сумме произведений зафиксированных цен на количество. Карточные данные обрабатывает внешний платёжный провайдер.

## Взаимодействия

- Покупатель и продавец используют Web по HTTPS. Web синхронно вызывает Users, Catalog, Feed и Orders по HTTP/JSON.
- Feed запрашивает товары у Catalog по HTTP/JSON.
- При оформлении Orders синхронно запрашивает у Catalog резерв и актуальные цены, сохраняет заказ и обращается к Payments по HTTP/JSON.
- Payments создаёт платёж у провайдера по HTTPS. Покупатель оплачивает его на внешней странице. Провайдер позже сообщает результат Payments отдельным HTTPS-запросом — webhook.
- Payments публикует результат в RabbitMQ, который доставляет его Orders. Orders обновляет статус и публикует событие для Notifications. Это асинхронное взаимодействие по AMQP.
- Notifications запрашивает email у Users по HTTP/JSON и передаёт письмо почтовому провайдеру по HTTPS.

Синхронные вызовы используются, когда нужен результат для продолжения операции. Уведомления обрабатываются отдельно, чтобы задержка отправки письма не блокировала заказ. Повторные события проверяются по идентификатору, неудачные отправки писем сохраняются для повторной попытки.

## Варианты архитектуры

**Вариант 1 — три крупных сервиса:** Accounts (пользователи), Commerce (каталог, заказы, платежи), Engagement (лента, уведомления). У каждого своя БД. Такой вариант проще запускать и сопровождать; внутри Commerce меньше сетевых обращений. Недостаток: каталог, заказы и платежи приходится обновлять и масштабировать вместе. Сбой одного модуля может затронуть остальные.

**Вариант 2 — шесть сервисов из таблицы.** Можно отдельно изменять ленту и платёжную интеграцию, масштабировать каталог и обрабатывать уведомления. Недостаток: больше приложений и сетевых вызовов, сложнее согласовать резервирование, заказ и оплату при сбоях.

**Выбран вариант 2:** обязанности из условия имеют явных владельцев, а персонализация, платежи и уведомления могут развиваться независимо. Каталог объединяет карточки, цены и наличие как связанные товарные данные. Принятый компромисс — более сложное взаимодействие сервисов ради независимых изменений. Для небольшого проекта вариант 1 мог бы быть проще.

## Запуск сервиса

Нужен запущенный Docker. Из папки проекта:

```bash
docker build -t marketplace-catalog .
docker run -d --name marketplace-catalog -p 127.0.0.1:8000:8000 marketplace-catalog
```

Открыть http://localhost:8000/health. Для проверки статуса:

```bash
curl -i http://localhost:8000/health
```

В Windows PowerShell использовать `curl.exe` вместо `curl`. Ожидается `200 OK` и JSON:

```json
{"status": "ok", "service": "catalog"}
```

Остановка и удаление контейнера:

```bash
docker stop marketplace-catalog
docker rm marketplace-catalog
```

Сервис написан на Python 3.12 и Flask. Dockerfile устанавливает Flask и запускает приложение командой `python -m flask --app app run --host=0.0.0.0 --port=8000`. `/health` проверяет только доступность HTTP-процесса; остальные GET-пути возвращают `404`. Базы, брокер и бизнес-операции на этом этапе не реализованы.
